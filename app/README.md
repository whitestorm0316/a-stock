# A股超跌反转 · 交互式选股器

## 启动

首次启动会加载 1000+ 万行面板并预计算全部因子，**约 80~100 秒**；之后常驻内存，
每次改参数的重算只需 **0.1~13 秒**。然后浏览器打开 `http://127.0.0.1:8770/`。

### Windows —— 双击即可

仓库根目录三个 `.cmd`，双击运行，不用开终端：

| 文件 | 作用 |
|---|---|
| `start.cmd` | **启动**（就绪后自动打开浏览器） |
| `stop.cmd` | 停止 |
| `update.cmd` | **每日更新**（停服务 → 增量拉取 → 重建面板 → 起服务，约 18 分钟） |

需要参数时再开命令行：

```bat
start.cmd --port 9000          :: 换端口
start.cmd --no-browser         :: 不自动开浏览器
update.cmd --no-rebuild        :: 只更新原始数据（约 10 分钟）
update.cmd --industry          :: 顺带刷新行业归属（建议每周一次）
```

Python 的查找顺序：环境变量 `ASTOCK_PY` → `%USERPROFILE%\.workbuddy\binaries\python\envs\default` →
仓库 `.venv` → PATH 上的 `python`。想固定某个解释器就设 `ASTOCK_PY`。

> 以前 `app/start.sh` 里写死了作者机器的 macOS Python 绝对路径，在别的机器上一跑就失败；
> 现已改为跨平台委派，Windows 用上面的 `.cmd`。

#### 控制台中文乱码 / 启动报 UnicodeEncodeError

中文 Windows 的 `cmd.exe` 默认代码页是 **936(GBK)**，而 Python 按控制台代码页决定
`sys.stdout` 的编码。于是启动信息里的中文会变成乱码，遇到 `✅` `🚀` 这类字符更是直接抛：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'
```

服务会**在加载完面板后崩掉**（白等 90 秒）。三道防线，都已内置：

1. `.cmd` 里执行 `chcp 65001`，把控制台切到 UTF-8 代码页 —— 中文正常显示；
2. `scripts/_console.py` 在启动时强制 `stdout/stderr` 走 UTF-8 且 `errors="replace"`
   —— 保证任何字符都**不会让进程崩掉**（最坏显示成 `?`，而不是 traceback）；
3. 输出里的 emoji 会按终端能力自动降级成 `[OK]` / `[>>]`（`mark()`）。

所以**双击 `.cmd` 一定是正常的**。若你是在自己开的终端里手动 `python app/server.py`，
先执行一次 `chcp 65001` 即可；不做也不会崩，只是中文可能是乱码。

### 统一控制入口 `scripts/ctl.py`

上面那些 `.cmd` / `.sh` 都只是薄壳，真正的逻辑在这里，三个平台共用：

```bash
python scripts/ctl.py status                  # 服务状态 + 数据文件清单
python scripts/ctl.py start                   # 启动（就绪后自动开浏览器）
python scripts/ctl.py start --port 9000
python scripts/ctl.py stop
python scripts/ctl.py restart
python scripts/ctl.py update                  # 每日更新（含重建面板，最后自动起服务）
python scripts/ctl.py update --no-rebuild --no-start
python scripts/ctl.py update --since 2026-09-01    # 回补某段区间
```

它替你处理了三件容易踩的事：① 自动释放被占用的端口；② 轮询 `/api/meta` 判断真正就绪
（加载期间访问一律 **502，不代表服务坏了**）；③ `update` 前先停服务
（服务常驻约 7GB，与重建面板抢内存会 OOM）。

日志：`logs/server-<port>.log`。启动失败时会自动打印日志尾部。

> ⚠️ 更新期间服务不可用，`update.cmd` 之前务必先在界面上导出好需要的东西。

## 默认参数（= 研究报告第 12 节验证的最优 3 条件策略）
| 条件 | 取值 |
|---|---|
| ① 超跌 | 距MA60 处于当日横截面 **D1**（最弱 10%） |
| ② 市值 | **最小 30%**（size_grp ≤ 2） |
| ③ 市场 | 全A等权净值 **< 其 MA60**（熊市） |
| 持有 | **20 日**（T+1 开盘买 → T+21 开盘卖），成本 0.3% 双边 |

实测：CAGR **29.9%** / MDD **−41.3%** / Sharpe **0.98** / 胜率 **58.5%** /
PF **2.19** / 正年份 **10/12** / 四段分期全为正。

## 六个功能页
1. **今日选股** — 列出符合条件的个股 + 关注度打分，可导出 CSV。
   熊市条件会让最新交易日经常无信号，此时自动**回溯**到最近有信号的交易日并提示。
2. **策略回测** — 8 个指标卡 + 仓位约束（双口径）+ 分持有期超额表 + 净值/回撤/逐年/四段图 + IS/OOS。
3. **交易明细** — 逐笔交易表（见下节）。
4. **参数寻优** — 勾选维度做网格搜索，按 Sharpe 排序（含负年份数与 OOS）。
5. **单股透视** — 查个股历史信号位置与后续表现（价格/均线/距MA60/量比）。
6. **研究结论** — 全部结论与两个方法学 bug 说明 + 免责声明。

左侧参数面板共 9 组：①~⑤ 选股条件、⑥ 自定义股票群（含**行业两级树**、**板块筛选**
与财务筛选）、⑦ 持有期、⑧ **仓位约束**（实盘可执行性）、⑨ **退市风险过滤**。

## 交易明细（逐笔可追溯）

「交易明细」页把回测里**每一笔交易**都摊开，用于核对策略到底赚在哪里、亏在哪里。

### 交易口径（固定持有期 · 与回测同源）
```
信号日 T（收盘后按条件选出）  →  T+1 开盘买入  →  持有 H 个交易日  →  T+1+H 开盘卖出
```
实现直接复用 `v3b_lib.simulate_hold()`，因此**交易笔数、胜率、盈亏比、PF 与「策略回测」页逐位一致**
（默认 K3：n_trade = 105,146、胜率 58.52%、单笔均值 4.525%、PF 2.1904，两处完全相同）。

每行给出：代码/名称/行业 · 信号日/买入日/卖出日 · 买入价/卖出价 ·
**净收益**（已扣 0.3% 双边成本）/毛收益/**同期基准**/**超额** · 盈亏标记 ·
市值组/距MA60 分位 · **该信号日当时已公告的财报**（营收/营收同比/归母/归母同比/报告期）。

### 页内功能
- **汇总卡片** 8 张：完成交易数/覆盖股票数、胜率、单笔均值与中位数、盈亏比/PF、
  最佳与最差、平均超额与跑赢基准比例、持有期与成本、交易区间。
- **单笔净收益分布直方图**（右偏是多头交易的典型形态）+ **逐年交易表现**（柱=平均净收益，线=胜率）。
- **逐年交易统计表**：交易数/盈利数/胜率/平均值/中位数/累计/盈亏比/最佳/最差。
- **最佳 20 笔 / 最差 20 笔**榜（超跌反转收益高度集中于少数极端反弹，如 2024-09「924 行情」；
  最差笔集中于「跌了还能再跌」的暴雷/退市股）。
- **明细表**：20 列，表头点击排序，支持**盈亏筛选**（全部/仅盈利/仅亏损）、
  **年份筛选**、**个股筛选**、每页 50/100/200 条、分页跳转、**导出 CSV**。
  亏损行浅红底色。筛选后会单独给出该子集的胜率/均值/中位数/累计/PF。
  第 4 列是**板块**徽章（主板/创业板/科创板/北交所）。

### 一个必须注意的口径区别
> 本页的单笔收益是「**每笔独立持有**」口径，**不是**同时发生的。
> 组合层面的 CAGR / MDD / Sharpe 请以「策略回测」页的**日度再平衡**口径为准，
> 两者**不可直接相乘或换算**。页面上也有同样的提示。

### 两种口径：不限仓位 vs 容量约束
本页跟随左侧 **⑧ 仓位约束** 的开关切换口径，**与回测页完全一致**：

| `params.max_pos` | 口径 | 列出什么 | `plan` 字段 |
|---|---|---|---|
| `0`（默认） | **不限仓位** | **全部**信号对应的交易（实盘做不完这么多） | `null` |
| `>0` | **容量约束** | 只能同时持 N 只 / 每日买 M 只时**真正建仓**的那批 | 诊断信息 |

默认 K3 参数下的对照（数据截止 2026-08-31）：

| 口径 | 列出笔数 | 说明 |
|---|---|---|
| 不限仓位 | 93,553 | 全部信号，平均同时持仓 943.9 只 |
| 10只/日3只 · 最超跌优先 | **781** | 计划建仓 787，其中 **6 笔未平仓**（见下） |

> 以上为 2026-09-25 之前的旧口径（允许同一只票重复持仓）。改口径后（全市场池实测）：
> 计划建仓仍 787、可结算 **780**、未平仓 **7**，详见「仓位约束」章节开头的说明。

容量约束口径下页面会多出一张**「仓位约束诊断」卡**，并替换掉顶部的口径说明（不再是黄色警示，而是紫色「📌 本页是仓位约束口径」），给出：

- **本次实际建仓** 787 笔（占全部信号 0.84%）
- **被丢弃信号** 93,413（99.2%，不补买）
- **本页可结算** 781 笔
- **期末未平仓** 6 笔

> ⚠️⚠️ **为什么「建仓数」（787）会大于「可结算数」（781）**
>
> 容量计划在建仓日只看「信号是否存在」，**不看持有期结束时数据是否还在**。
> 落在**数据末尾最后 H（=20）个交易日内**建的仓，买入后持有期**还没走完就到数据边界**了，
> 因此算不出卖出价。这批头寸实盘里就是**还拿在手上**，本页用 `n_open` 单独报告：
> **不计入明细**，也**不计入胜率等统计** —— 否则会因缺少结局而偏乐观。
>
> 顺带一个容易写错的地方：文案必须说「**最后 H 个交易日内**」（时间窗口），
> 而不是「n_open 个交易日内」—— 后者是**笔数**，凑巧数值接近但含义完全不同。

导出的 CSV 文件名也会带容量标记（如 `..._H20_cap10x3.csv`），
**避免把容量口径的明细导出成不限仓位的口径**。

### 接口
```
POST /api/trades
  params / pool                策略参数与股票池（同 /api/backtest）
                               ← params.max_pos / max_new / pick 决定口径
  cost                         单边成本率，默认 0.003
  sort / order                 排序字段与方向（默认 exit_date / desc）
  page / page_size             分页（page 从 1 起，page_size 上限 500）
  win                           true=仅盈利 / false=仅亏损 / 省略=全部
  year                          按买入年份筛选
  code                          按个股筛选（支持 6 位数字）
  min_ret / max_ret             按净收益率区间（小数）
  with_rows                     false 时只返回汇总（省流量）

POST /api/export  { kind:"trades", ... }   导出逐笔明细 CSV（支持 win / year 筛选）
```
`/api/backtest` 响应额外附带 `trade_brief`（交易数/胜率/均值/最佳最差/PF/超额/分布直方图），
无需再拉一次明细即可在回测页展示交易概况。
⚠️ `trade_brief` 也**跟随容量口径**：`max_pos>0` 时它统计的是「实际建仓」那批
（并带 `plan` 子对象），否则会出现「容量诊断说建仓 787 笔、交易摘要说 93,553 笔」的自相矛盾。

`/api/trades` 在 `max_pos>0` 时返回额外的 `plan` 对象：
`{ max_pos, max_new, pick, pick_name, n_signal, n_drop, drop_pct, n_plan, n_open }`。

## 自定义股票群（左侧第 ⑥ 组）
- **自定义代码清单**：输入 6 位代码或 `000001.SZ` 形式，逗号/空格分隔；
  可点「载入当前候选」把今日选股结果一键转为股票池。
- **行业筛选**：**两级树** —— 门类（证监会 A~S）→ 细分行业（同花顺 88 个），多选。见下节。
- **板块筛选**：主板 / 创业板 / 科创板 / 北交所，多选（默认选中前三，北交所不选）。
- **交易所**：沪市 / 深市 / 北交所（北交所流动性弱，默认不选）。
- **财务筛选**：见下节。

### 行业筛选：两级树（门类 → 细分行业）

原来是一个平铺的 88 项复选框列表，太长、难找。现在改成两级：

```
▸ [ ] A  农、林、牧、渔业            2 行业 · 63 只
▸ [ ] B  采矿业                      3 行业 · 65 只
▾ [x] C  制造业                     56 行业 · 3,761 只
      ☑ 半导体   ☑ 通用设备   ☑ 专用设备   …（展开后逐个勾选）
▸ [ ] D  电力、热力、燃气及水生产和供应业   2 行业 · 137 只
…
    H  住宿和餐饮业                    本数据源无细分行业
```

交互约定：

| 操作 | 行为 |
|---|---|
| 点**门类左侧方框** | 全选 / 全不选该门类下的全部细分行业（三态：全选 · 半选 · 未选） |
| 点**门类名称行** | 展开 / 收起该门类（不会碰勾选状态） |
| 「展开全部」按钮 | 一次展开或收起所有门类 |
| 顶部搜索框 | 按细分行业名过滤（**大小写不敏感**），命中的门类自动展开，清空后恢复原展开状态 |
| 「全选」/「清空」 | 作用于全部 **88 个细分行业**（不是 15 个门类） |

> **请求体契约不变**：前端仍然只把**细分行业名**的扁平清单放进 `pool.industries`，
> 门类只是一个「批量勾选」的 UI 控件，**门类代码（A/B/C…）绝不会进入请求体**。
> 所以后端过滤逻辑一行都没改，两种选法完全等价：
> 勾「C 制造业」≡ 逐个勾上 C 下的 56 个细分行业。
> `tests/test_indtree.js` 专门守住这条契约。

#### 门类是怎么来的（重要局限）

数据源**只有同花顺行业指数（881xxx.TI）的 88 个细分行业，没有任何门类字段**
（见 `scripts/20_fetch_industry.py` 的说明）。所以门类这一层是
**按 `app/industry_tree.json` 做的人工归并**，不是官方分类：

1. 同花顺细分行业 ≠ 证监会小类，边界并不一致。一个细分行业里混着不同门类的个股时，
   只能整体归到**多数派**所在的门类，无法按个股拆分。`industry_tree.json` 里
   每个门类都带 `notes`，逐一标注了这类情况。
2. 几个容易误判的例子（都已在配置里注明理由）：
   - 「**汽车服务及其他**」名字像服务业，实际成分以摩托/两轮车整车与零部件为主
     （春风动力、爱玛科技、隆鑫通用、九号公司…）→ 归 **C 制造业**
   - 「**旅游及酒店**」成分以景区运营为主（黄山旅游、峨眉山A、丽江股份、长白山…），
     景区管理在证监会口径下属「公共设施管理业」→ 归 **N**；成分里的酒店实际属 H、
     免税属 F、演艺属 R，无法拆分
   - 「**工业金属 / 小金属 / 能源金属**」以冶炼加工为主 → 归 **C**（矿采选部分属 B）
   - 「**医药商业**」是流通批发零售 → 归 **F**（不是 C 制药，也不是 Q 卫生）
   - 「**环保设备**」是设备制造 → 归 **C**；对应的运营治理在 N（环境治理）
3. 门类 **H / L / M / O 在数据源里没有对应的独立细分行业**，相关个股散落在别的行业里，
   所以界面上把这四类如实列出并标注「本数据源无细分行业」（悬停看原因），而不是假装它们为空：
   - **H 住宿和餐饮业** → 酒店类个股被并进「旅游及酒店」
   - **L 租赁和商务服务业** → 广告营销混杂在「文化传媒」内
   - **M 科学研究和技术服务业** → 检测/设计咨询散落在「建筑装饰」「汽车服务及其他」
   - **O 居民服务、修理和其他服务业** → A 股标的极少
4. 界面上还有一个「**未归类**」兜底组，装的是「面板里有、配置却没归类」的细分行业。
   实测它必然包含一项 **`未知`** —— 这是个股缺少行业映射时的兜底值（数据源未收录）。
   这个组的作用是**防止配置漂移导致某些行业静默消失**：如果哪天重跑了
   `20_fetch_industry.py` 导致行业增删改名，漏配的行业会出现在这里，而不是凭空不见。

#### 校验配置

```bash
python scripts/check_industry_tree.py
```

会做三件事：① 与 `data/raw/industry_map.json` **双向对账**（配置写错的行业名、
漏配的行业都会报出来）；② 检查同一细分行业是否被归到多个门类；③ 对照证监会
2012 版 A~S 门类表校验代码与名称。当前结果：**88/88 全覆盖、无重复、15 个门类有成员**。

改了行业清单（重跑 `20_fetch_industry.py`）后，**务必跑一次这个脚本**。

### 板块筛选是怎么判定的

板块**不靠代码号段猜**，而是直接读面板自带的 `board` 列（数据源官方分类，
取值 `MAIN` / `CHINEXT` / `STAR` / `BJ`），并用**涨跌停幅度**做交叉验证：

| 板块 | 代码号段（兜底用） | 涨跌停幅度 | 只数 |
|---|---|---|---|
| 主板 `MAIN` | 沪 600/601/603/605 · 深 000/001/002/003/302 | ±10% | 3,046 |
| 创业板 `CHINEXT` | 300/301 | ±20% | 1,352 |
| 科创板 `STAR` | 688/689 | ±20% | 595 |
| 北交所 `BJ` | 920 / 8xxxxx / 4xxxxx | ±30% | 311 |

> ⚠️ **302 号段属深市主板，不是创业板** —— 用 `limit_pct` 验证过：
> `302132.SZ 中航成飞` 只有 5%/10% 涨停记录，创业板应为 20%。
>
> **自检手法**：若某板块出现 20% 涨停却不属于创业板/科创板，说明分类错了。

板块与交易所是**两个独立维度**（`board × exchange` 交叉表完全干净：创业板全在深市、
科创板全在沪市、北交所自成一类），筛选时取**交集**。所以选「北交所」板块时，
必须同时把交易所的「北交所」也勾上，否则交集为空 → 提示「信号数过少」。

实测各板块单独回测（默认参数，持有 20 日）：

| 股票池 | 信号数 | CAGR | Sharpe | 胜率 | 单笔均值 | MDD |
|---|---|---|---|---|---|---|
| 主板 | 48,009 | 29.72% | 1.033 | 57.9% | 3.77% | −39.7% |
| 创业板 | 28,785 | 22.23% | 0.763 | 61.0% | 4.82% | −45.5% |
| 科创板 | 17,406 | 5.35% | 0.336 | 54.9% | 4.02% | −51.5% |
| 北交所 | 11,708 | 11.93% | 0.538 | 60.4% | 7.67% | −47.3% |
| 主板+创业板+科创板 | 94,200 | 26.67% | 0.911 | 58.3% | 4.14% | −41.1% |
| 全部（含北交所） | 105,908 | **29.93%** | **0.982** | **58.5%** | **4.52%** | −41.3% |

> 最后一行的数字与研究报告完全一致，说明板块筛选是**纯分区、无泄漏**。
> 有意思的是：科创板的单笔均值不低（4.02%）但 CAGR 只有 5.35% ——
> 因为它的信号集中在少数时段，**资金利用率低**。单笔收益与组合收益不是一回事。

### 关于「市值组」列（M1~M10）

`size_grp` 是面板给的**分位序号**（0 = 最小 10%），不是十分位**档位编号**。
早期版本直接渲染成 `D0`/`D2`，与旁边真正的档位列「距MA60 D1~D10」混淆，
现统一显示为 `M1`~`M10`（M1 = 最小 10%，M10 = 最大 10%）。

## 财务筛选（动态 · 无前视偏差）

在股票池中加入基本面维度：**营业总收入**、**营收同比**、**归母净利润**、**归母同比**，
以及「只看某类报告期」（Q1 / 半年报 / Q3 / 年报）。单位：营收与利润填**亿元**，同比填 **%**。

### 为什么是「动态」的

财报有**披露日**。回测任意交易日 T 时，只能使用 `披露日 ≤ T` 的财报——
否则就是用「未来才知道的数字」去选「过去的股票」，回测必然虚高。

本工具的 `engine.py::_build_financials()` 对每个「股票 × 交易日」单元格
用 `searchsorted` 找「披露日 ≤ T」的最后一期财报，把该期的营收/利润/同比写进去：

```
交易日 2026-04-01 → 生效 2025Q3（2025-10-30 披露）
                    2025 年报要到 2026-04-17 才披露，此刻看不到 ✅
交易日 2026-05-06 → 生效 2026Q1（2026-04-25 披露）✅
```

### 前视偏差的实测代价

| 做法 | 信号数 | CAGR | Sharpe |
|---|---|---|---|
| **动态 as-of（本工具）** | 25,941 | **26.4%** | 0.89 |
| 静态用最新财报（常见错误） | 26,214 | 30.0% | 0.97 |

→ 用静态财报筛股会**虚高约 3.5 个百分点**。这就是必须做动态对齐的原因。

### 数据来源与口径

| 项 | 来源 | 说明 |
|---|---|---|
| 营收 / 归母净利润 | 同花顺 fuyao `income-statements` | **累计(YTD)** 口径，Q2 = 上半年累计 |
| 财报披露日 | 东方财富 `RPT_PUBLIC_BS_APPOIN` | 真实披露日（**86.3%** 覆盖）；缺失时用法定披露截止日兜底 |
| 覆盖 | 5,565 只 × 2014Q1~2026Q2 | 231,552 行，每只中位 46 期 |

**同比增长**用「去年同期同报告期」直接对比（如 2026Q2 vs 2025Q2），因为原始数据已是累计值。

重建数据：`python scripts/fetch_fin_announce.py --step all`（约 5 分钟）。

### 重要发现

叠加财务条件后 **CAGR 多数情况略低于纯价格 K3**（29.9% → 21~28%）：

| 组合 | 信号 | CAGR | MDD | Sharpe |
|---|---|---|---|---|
| K3 基线 | 105,908 | **29.9%** | −41.3% | **0.98** |
| K3 + 营收同比>0 | 56,185 | 25.8% | −40.4% | 0.88 |
| K3 + 营收同比>20% | 25,941 | 26.4% | −42.1% | 0.89 |
| K3 + 归母同比>0 | 38,680 | 28.4% | **−39.8%** | 0.96 |
| K3 + 营收>10亿 | 18,485 | 21.0% | −43.2% | 0.76 |
| K3 + 营收>10亿 + 归母同比>0 | 7,406 | 21.2% | −46.4% | 0.75 |

这不是 bug，而是超跌反转策略的特性：**跌得最惨的票反弹最猛**，
但它们往往也是基本面最差的。加财务条件是「用收益换确定性」——
若你的目标是**降低回撤**，`+归母同比>0` 把 MDD 从 −41.3% 改善到 −39.8% 且 CAGR 只掉 1.5pp，
性价比最好。

## 仓位约束（实盘可执行性 · 左侧第 ⑧ 组）

> ### ⚠️ 口径变更（2026-09-25）：同一只票不得重复持仓
>
> 旧版允许**同一只票在未平仓期间反复买入**：默认参数下会产生 **392 次**「上一笔还没到期、
> 又买同一只」的建仓，单只票最多同时挂着 **4 笔**仓位。这既不真实（等于对单一标的加杠杆），
> 也让「同时持仓 10 只」形同虚设（实际只有 3~4 只不同的票）。
>
> 现改为：**某只票只要还有未平仓的仓位，就不再买入；这笔仓位卖出之后立刻恢复交易**
> （受 T+1 下单约束，最早在卖出日的**下一个交易日**重新买入）。实现在 `v3b_lib.plan_positions(stock_of_row=..., dedupe=True)`。
>
> 撞上「已持有」的候选时会**顺延到下一位候选**（模拟「这只拿着了，买下一只」），
> 而不是浪费当天买入额度；被判重复的信号计入 `n_drop_dup`，UI 的诊断卡会单独列出。
>
> **下面所有表格是旧口径（允许重复持仓）的结果，仅作对照，与实际页面已不一致。**
> 新口径实测（K3，主板+创业板+科创板，94,143 信号，数据截至 2026-09-24）：

| 配置 | 实际建仓 | 因重复跳过 | 已投资金 CAGR | 账户资金 CAGR | Sharpe(账户) | MDD(账户) | 平均持仓 |
|---|---|---|---|---|---|---|---|
| 10只/日3只 | 787 | 7,107 | **40.00%** | **33.13%** | 1.096 | −42.72% | 8.6 |
| 20只/日3只 | 1,495 | 13,226 | 34.73% | 32.00% | 1.152 | −40.91% | 15.7 |
| 50只/日3只 | 3,188 | 27,152 | 31.65% | 23.73% | 0.998 | −37.61% | 32.1 |

随机对照同步更新（10只/日3只，200 次随机选股）：
随机账户 CAGR 均值 **18.99%**（sd 2.81%，P5 14.54%，P95 23.59%），
「最超跌优先」33.13% 落在 **z = 5.03** —— 选股规则显著优于随机，结论不变。

### 为什么必须加这一层

上面所有指标的默认口径是**不限仓位**：某日有 500 个信号，就等权买入 500 只。
实测默认 K3 策略的**平均同时持仓 943.9 只** —— 个人资金根本做不到，
所以那个 29.9% 的 CAGR 是**学术口径**，不是你能拿到的收益。

打开「⑧ 仓位约束」，就可以按真实下单节奏重算：

```
每个交易日：先卖出到期仓位  →  看当日新信号  →  排序取前 max_new 个
           →  受 max_pos 上限截断  →  被丢弃的信号不补买（保守假设）
```

### ⚠️⚠️ 两种口径（最容易搞错的地方）

| 口径 | 日收益算法 | 用途 |
|---|---|---|
| **已投资金** | `Σ持仓收益 / 持仓只数` | 与「不限仓位」基线**可直接对比**，但假设闲置资金也在赚钱 → **高估** |
| **账户资金** | `Σ持仓收益 / 同时持仓上限` | 资金按 `max_pos` 份等分，空着的那份赚 0 → **这才是账户里真实看到的收益率** |

两者之比 = **资金利用率**（`平均持仓 / max_pos`）。

### 实测结果（默认 K3，主板+创业板+科创板）

**容量曲线**（固定每日 3 只，扫描同时持仓上限）：

| 同时持仓 | 实际建仓 | 丢弃% | 已投资金 CAGR | 平均持仓 | IS 年化 | OOS 年化 |
|---|---|---|---|---|---|---|
| 不限 | 94,200 | 0.0% | 26.67% | 943.9 | 31.82% | 21.38% |
| 5 只 | 410 | 99.6% | 31.11% | 4.6 | 30.24% | 32.05% |
| **10 只** | **787** | **99.2%** | **35.39%** | **8.6** | **29.32%** | **42.20%** |
| 20 只 | 1,495 | 98.4% | 36.38% | 15.8 | 30.15% | 43.38% |
| 30 只 | 2,142 | 97.7% | 38.21% | 22.1 | 37.07% | 39.45% |
| 50 只 | 3,197 | 96.6% | 40.04% | 32.2 | 40.91% | 39.11% |
| 80 只 | 3,726 | 96.0% | 42.01% | 37.3 | 42.18% | 41.83% |

（80 与 120 只结果相同 → 「每日 3 只」在此处成为 binding，总建仓封顶 **3,726 笔**）

**用户关心的 10 只 / 日 3 只（账户资金口径）**：

|---|---|---|---|---|---|---|

### 两个反直觉的结论

**① 受限组合反而跑赢「不限仓位」基线**（已投资金口径 35.39% vs 26.67%）。
原因不是约束本身有魔力，而是**选股规则本身有 alpha**：对同一批信号，在当日横截面内
再按「距MA60」分 5 档，最超跌档的单笔净收益显著高于最不超跌档：

| 档位 | 笔数 | 均值 | 中位 | 胜率 |
|---|---|---|---|---|
| Q1 最超跌 | 19,202 | **5.27%** | 3.24% | 59.6% |
| Q2 | 18,718 | 4.26% | 2.63% | 58.3% |
| Q3 | 18,696 | 3.73% | 2.26% | 57.4% |
| Q4 | 18,718 | 3.69% | 2.32% | 58.0% |
| Q5 最不超跌 | 18,216 | **3.69%** | 2.35% | 58.1% |

Q1−Q5 = **+1.58pp（t=9.01, p=2.07e-19）**，单调递增；
**12 年中 11 年为正**；且 **OOS(2021-26) 的差 (+2.01pp) 比 IS(2015-20) 的 (+1.06pp) 更大** ——
样本外更强，不是过拟合。

**② 「每日买入上限」几乎不 binding**。
有信号日平均 **75.8** 个信号（P50=69，P95=141，P100=316），99.9% 的交易日信号数 > 3。
但一旦「同时持仓」被限到 10 只，稳态下每天只需建仓 **0.5 只**就能维持满仓 ——
所以「每日 3 只」只是防手滑的安全阀，真正起作用的是**同时持仓上限**。

反过来，每日上限**越松反而越差**（同时 10 只固定）：

| 每日上限 | 建仓 | CAGR | Sharpe | 平均持仓 | 满仓日占比 |
|---|---|---|---|---|---|
| 1 只 | 714 | **37.58%** | 0.923 | 7.4 | 21.0% |
| 2 只 | 768 | 36.79% | 0.983 | 8.2 | 38.5% |
| **3 只** | **787** | **35.39%** | **0.999** | **8.6** | **41.5%** |
| 5 只 | 815 | 30.32% | 0.950 | 9.2 | 51.2% |
| 10 只 | 840 | 23.55% | 0.821 | 10.0 | 57.9% |

因为上限越松，当日被迫**同时**买入越多只、排序越靠后（越不超跌）的候选。

### 选股规则有效性检验（随机对照）

信号远多于仓位时，必须回答「先买哪只」。系统内置 7 条规则
（最超跌优先 / 成交额优先 / 小市值优先 / 大市值优先 / 60日跌幅优先 / 随机 / 原始顺序），
**全部只用信号日 T 当日收盘可见的字段**，无前视偏差。

后端会额外跑 **200 次随机选股**作为对照分布。实测（10只/日3只，账户口径 CAGR）：

- 随机：均值 **19.03%**、sd 3.07%、P5 13.78%、P95 24.14%、区间 [11.70%, 28.03%]
- 最超跌优先：**31.24%** → 落在第 **100** 百分位，**z = 3.98**

即「最超跌优先」显著优于随机选股（z > 2），这个规则确实带来了超额。

| `max_new` | 3 | 每日最多新建仓数 |

## 退市风险过滤（左侧第 ⑨ 组）

回测里最难看的一类亏损是「跌了还能再跌」的**退市/准退市股**。这一组把
**规则上已经踩到退市红线**的票从候选池里剔掉。默认全关（= 研究报告原始口径）。

> ### ⚠️ 纪律：只用买入日 T **已经公开**的信息
>
> 三条判据都严格按信号日 T 的可知信息构造，**不含任何未来数据**：
>
> | 判据 | 取数口径 |
> |---|---|
> | 财务类 / 连续两年亏损 | 财报取 **实际披露日 ≤ T** 的最新一期（沿用财务筛选的 as-of 对齐逻辑） |
> | 面值退市 | 用**未复权**收盘价算 T 之前 20 个交易日的滚动窗口 |
>
> 目的**不是预测谁会退市**（那是另一个问题，且必然前视），而是剔除「按现行规则
> 已经被点名/已触及量化标准」的票。

### 三条判据

| 判据 | 规则 | 面板实现 |
|---|---|---|
| **财务类退市风险** | 退市新规组合指标：年化归母净利 < 0 **且** 年化营收 < 门槛 | `delist.financial`，门槛 `delist_rev_floor`（默认 1 亿） |
| **连续两年亏损** | 最近两个年度的**年报**归母净利均为负 | `delist.loss2y` |
| **面值退市倒计时** | 连续 20 个交易日收盘价 < 1 元 → 终止上市 | `delist.penny`，阈值 `delist_penny_days`（默认 10/20） |

**营收门槛的两套标准**：2020 退市新规为 1 亿；**2024-04 修订后主板提到 3 亿**
（双创、北交所仍 1 亿）。勾上「主板按 2024 新规」即启用 3 亿口径。

**为什么面值默认 10/20 而不是规则的 20/20**：本面板里 **20/20 命中 0 行** —— 因为
`v3b_lib.load_clean` 已先行剔除了 ST 股与次新股，等真跌破 1 元时往往早就不在样本内了。
所以默认取 10/20 作为「已逼近面值退市」的预警口径，可在 1~20 之间调。

### 实测剔除量（默认 K3，主板+创业板+科创板，数据截至 2026-09-24）

基准（全关）：**105,851 信号 / 3,671 只股票**。

| 判据 | 剔除信号 | 占基准 | 涉及股票 |
|---|---|---|---|
| 财务类退市风险 | −3,377 | 3.19% | 154 |
| 连续两年亏损 | −8,839 | 8.35% | 536 |
| 面值退市 10/20 | −34 | 0.03% | 7 |
| 面值退市 20/20（规则原线） | **0** | 0.00% | 0 |
| 财务 + 连续两年亏损 | −11,206 | 10.59% | 611 |
| **三条全开** | **−11,206** | 10.59% | 611 |
| 三条全开 + 主板 2024 新规 | −12,907 | 12.19% | 655 |

> **一个值得注意的结果**：「三条全开」与「财务+连续两年亏损」的剔除量**完全相同**。
> 那 7 只面值预警股**全部**同时命中了财务/亏损判据 —— 会跌到 1 元附近的票，
> 基本面基本都已经烂透了。所以面值判据在这里更像**冗余的安全带**，而不是独立增益。

对收益的影响（不限仓位口径）：

| 配置 | 信号数 | CAGR | MDD | 胜率 |
|---|---|---|---|---|
| 基准（全关） | 105,851 | 30.05% | −41.30% | 58.52% |
| 三条全开 | 94,645 | 29.03% | −41.48% | 58.23% |
| 三条全开 + 2024 新规 | 92,944 | 28.96% | −41.47% | 58.22% |

即：剔掉 10.6% 的信号，CAGR 只降约 **1 个百分点**，回撤与胜率基本不动。
**这是一个「几乎免费的保险」** —— 代价很小，换来的是持仓里不再出现踩退市红线的票。

### ⚠️ 为什么没有「剔除 ST」这一项

这是本功能**唯一想做但数据上做不到**的判据，过程值得记录：

1. 面板里的 `is_st_now` 是**按当前股票名称**判断的，**含未来信息**（用今天的名字判断 2018 年），
   直接拿来过滤就是前视偏差。而且 `v3b_lib.load_clean` 已经据此默认剔除了「截至今天仍是 ST」
   的 **204 只**票。
2. 要按「**当时**是否 ST」过滤，需要**历史名称/历史风险警示**数据 —— 本数据源没有。
3. 曾试过用**涨跌幅限制 5%** 反推 ST：
   ```
   limit_pct == 0.05  →  判为 ST
   ```
   实测**失败**：全面板 **40.39%** 的行都命中 5%，因为 `limit_pct` 对
   「**从未触及涨跌停**」的行填的是兜底值 5%，把正常股票全捞进来了。
   该方案已**整体移除**（不留开关，避免给用户一个假选项）。

### 五个必须知道的注意点

1. **fixtures 是快照，改了后端响应就要刷新**：
   ```bash
   python app/server.py 8772 &     # 先起服务
   python tests/make_fixtures.py   # 抓快照（默认 8772）
   ```
   忘了刷新的话，新加的字段在快照里不存在，断言会误报失败。
   容量口径的那份是 `fixture_trades_cap.json`（前端按 `params.max_pos` 分流取不同快照）。

2. **七套 jsdom 不要并行跑** —— 同时驻留内存会触发 OOM（`SIGTERM 137`）。
   `run.sh` 已做成逐条串行。

3. **CDP 测试先等按钮可用**：前端 `init()` 会自动跑一次回测（约 14s），
   期间 `#run` 是 `disabled`，此时点击会被**静默忽略**。
   `cdp_cap.js` 里用 `waitFor('!#run.disabled && 结果已渲染')` 处理；
   并且必须先切到「策略回测」Tab，否则图表在隐藏容器里会退化成 100px 宽。

4. **CDP 收集未捕获异常必须用 `Page.addScriptToEvaluateOnNewDocument`**，
   且注册后要**再显式 `Page.navigate` 一次**。原因：`/json/new?<url>` 创建标签页时
   文档可能已经在加载，此时 `Runtime.evaluate` 注入的 `window.__errs` 会被随后的
   文档加载**整个清掉** → 最后读到 `undefined`（本脚本栽过两次）。

5. **启动慢是正常的（首次约 80 秒）**，因为要加载 3.7G 面板并预计算。
   期间 curl 会返回 **502**（连接被拒/代理错误页），**这不代表服务坏了**。
   用端口占用 + 轮询 `/api/meta` 判断：
   ```bash
   lsof -nP -iTCP:8772 -sTCP:LISTEN                 # 端口是否在听
   for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code}\n" \
     --max-time 5 http://127.0.0.1:8772/api/meta; sleep 8; done
   ```
   ⚠️ 另有两个坑：① `start.sh` **默认端口是 8770**，要跑 8772 必须显式传参
   `bash app/start.sh 8772`；② 用 `nohup ... &` 起的进程会**随 shell 退出被回收**，
   要用后台任务方式启动。

## 图标

浏览器标签页、手机主屏、PWA 独立窗口共用 `app/icons/` 一套，**没有构建步骤**：
`icon.svg` 是手写的矢量源，PNG 由 `scripts/make_icons.py` 用 headless Chrome 光栅化。

| 文件 | 用途 |
|---|---|
| `icons/icon.svg` | 主图标（512 视口）。**装了哪一套，改这一个文件就行** |
| `icons/icon-mark.svg` | 无底字形，viewBox 裁到边缘。页面头部内联用的就是同一形状 |
| `icons/icon-16/32/64.png` | 标签页兜底（Safari 对 SVG favicon 支持不稳） |
| `icons/icon-180.png` | `apple-touch-icon`，iOS 加到主屏 |
| `icons/icon-192/512.png` | PWA 清单用，512 同时声明为 `maskable` |
| `icons/concept-a/b/c.svg` | 三个设计方向（见下），几何完全一致，可互换 |
| `site.webmanifest` | PWA 清单：`display:standalone`、`theme_color` 同图标底色 |

### 设计

```
   ╲                       绿色跌段（--dn #2ea06a）：超跌
    ╲
     ╲___
         ╲╱  ← 反转点       深色圆角底（--blue #3266ad → 深蓝渐变）
         ╱
        ╱  ↗                红色涨段（--up #e04a4a）+ 箭头：反转向上
```

- **配色直接取自页面 `:root`**，不是另起一套。注意**红涨绿跌**是中国市场惯例，
  别按欧美习惯反过来。
- **只用图形不用文字**：中文字形在 16px 下必然糊掉。
- 底部圆角 116/512（≈22.7%），接近 iOS 的 squircle 曲率；外加一道
  `stroke-opacity=.16` 的白色细边，**深色标签栏上才不会糊成一团**。
- 内容全部落在中心 80% 的圆形安全区内，`maskable` 裁切成圆形也不会切到图形。
- 头部 h1 里的字形是**内联 SVG 而非 `<img>`** —— `index.html` 保持单文件可用，
  直接用 `file://` 打开也不会缺图。

### 三个候选方案

| 方案 | 隐喻 | 小尺寸（16px）表现 |
|---|---|---|
| `concept-a` ★ **当前** | **反转钩**：绿段超跌 → 红段带箭头反转向上 | 最好，箭头在任何尺寸都读得出方向 |
| `concept-b` | **阈值突破**：一排候选柱，只有最右一支越过虚线阈值 | 一般，虚线在 16px 下消失 |
| `concept-c` | **A 字**：绿腿 + 红腿 + 白横杠组成「A」 | 好，「A」辨识度高，但语义偏品牌不偏功能 |

换方案（三案几何一致，换完视觉体量不跳）：

```bash
cp app/icons/concept-c.svg app/icons/icon.svg
python scripts/make_icons.py app/icons/icon.svg app/icons 16 32 64 180 192 512
bash tests/run.sh icon          # 必须过
```

### 重新光栅化 / 改样式后人工核对

```bash
python scripts/make_icons.py app/icons/icon.svg app/icons 16 32 64 180 192 512
python scripts/make_icons.py --sheet app/icons output/icon-sheet.png
```

**为什么用 Chrome 而不是 Python 库**：SVG 里有渐变、圆角、透明度，纯 Python 侧没有可靠
渲染器（cairosvg 需要 cairo 原生库，Windows 上很折腾）。Chrome 本来就要跑前端测试，直接复用。

⚠️ **`--force-device-scale-factor=1` 不能去掉**：一旦失效，512 的图会被渲成 1024 或 384，
肉眼在浏览器里看不出来，但 iOS 主屏图标会糊。`tests/test_icon.js` 直接读 PNG 的 IHDR
块比对文件名尺寸，就是守这条。

### 服务端要为图标做的两件事

1. **Content-Type**：`/static/` 原先把未知扩展名回 `application/octet-stream`，
   而浏览器拿到 `octet-stream` 的 favicon 会**直接拒绝渲染**。已在 `server.py`
   的 `_STATIC_CTYPES` 里显式声明 `svg / png / webmanifest / ico / woff2`。
2. **目录穿越防护**：`/static/` 会拼接到磁盘路径，`/static/../server.py` 这类请求
   本来能读到源码。`_serve_file()` 现在用 `realpath` 校验解析后的路径必须落在 `app/` 内。

## 接口
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/meta` | 元信息（交易日范围、88 个细分行业 + `industry_tree` 两级归类、股票清单、`fin_avail`） |
| GET | `/api/defaults` | 默认参数 + 11 个预设方案 + 选股规则清单 `pick_rules` |
| POST | `/api/scan` | 今日选股（返回含 `fin_rev`/`fin_rev_yoy`/`fin_np`/`fin_np_yoy`/`fin_end`/`fin_q`） |
| POST | `/api/backtest` | 策略回测（附带 `trade_brief` 交易摘要；`max_pos>0` 时附 `capacity` 仓位约束块） |
| POST | `/api/trades` | 逐笔交易明细（分页/排序/盈亏/年份/个股筛选） |
| POST | `/api/tune` | 参数寻优 |
| GET | `/api/stock?code=` | 单股透视 |
| POST | `/api/export` | 导出 CSV：`kind:"candidates"`（默认）候选股 / `kind:"trades"` 逐笔明细 |

### 回测/选股参数中的财务字段
```
rev_min / rev_max          营业总收入（元）
rev_yoy_min / rev_yoy_max  营收同比增长率（小数，0.2 = +20%）
np_min / np_max            归母净利润（元）
np_yoy_min / np_yoy_max    归母净利润同比增长率
fin_period                 latest | q1 | q2 | q3 | q4
```

### 回测参数中的仓位约束字段
```
max_pos   同时持仓上限（0 = 不限仓位，默认）    → 各预设方案均为 0
max_new   每日最多新建仓数（默认 3）
pick      信号超额时的排序规则（默认 deep = 最超跌优先）
n_sim     /api/backtest 请求体可选，随机基准模拟次数（默认 200）
```
`max_pos > 0` 时，`/api/backtest` 的响应里会多出一个 `capacity` 块，
含 `cagr/cap_cagr`（已投资金 / 账户资金两种口径）、`avg_pos`、`drop_pct`、
`rand_mean/rand_sd/rand_p05/rand_p95/z`（随机对照）、`yearly`、`segs`、`nav_cap`。
`/api/defaults` 新增返回 `pick_rules`：可用的选股规则清单（id / name / desc / default）。

### `/api/meta` 中的行业字段（左侧第 ⑥ 组两级树的数据源）
```
industries          88 个细分行业名（扁平清单，**前端实际发回后端的也是这一层**）
industry_tree       [{code:"C", name:"制造业", subs:[...], n_sub:56, n_stock:3761, notes:[...]}, ...]
                    只含 subs 非空的门类（当前 15 个）
industry_absent     [{code:"H", name:"住宿和餐饮业", why:"..."}, ...]
                    本数据源无细分行业的门类（当前 H/L/M/O 共 4 个）
industry_unlisted   面板里有、配置未归类的细分行业（当前 ["未知"]）
industry_unlisted_n 上述未归类项的股票数合计
```
门类来自 `app/industry_tree.json`（人工归并，局限见该文件头部与上文「门类是怎么来的」）。
**请求参数里没有「门类」这一层** —— 前端勾门类只是批量勾上其下的细分行业，
发回来的仍是 `industries` 扁平清单，所以后端过滤逻辑不受影响。

### 回测/选股参数中的退市风险过滤字段（左侧第 ⑨ 组）```
delist                 {financial: bool, loss2y: bool, penny: bool}
                       三条判据的开关，默认全 false（= 研究报告原始口径）
                       注意：没有 st 键 —— 见上文「为什么没有剔除 ST 这一项」
delist_rev_floor       营收门槛（元），null → 用默认 1e8（1 亿）
delist_main_2024       true 时主板门槛提到 3e8（2024 新规），双创仍 1 亿
delist_penny_days      近 20 日中低于面值线的天数阈值，null → 用默认 10
```
启用后，这三条会以 `非财务类退市风险` / `非连续两年亏损` / `非面值退市`
的名字出现在响应体的 `conditions` 数组里（前端直接用这个数组渲染生效条件）。
`/api/meta` 不含这些字段；`/api/defaults` 的 `defaults.delist` 给出默认开关状态。
